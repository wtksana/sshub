# 日志高亮正式版负载对比

2026-11-18，Windows x64。默认 2 MiB 历史预算下，八会话各约 1,000 条逻辑行／秒，关闭与开启高亮分别完成十分钟负载。两轮全程八连接，开启轮全程八会话启用，降级计数均为零。高亮增加了 CPU 成本；本次没有测量最高渲染吞吐、帧率或端到端输入延迟。

用户在两轮结束后明确取消 8／32／64 MiB 的资源采样；四档功能保留，本文不提供这些档位的内存或性能结论。

## 环境与构建

- Windows 11 家庭版 10.0.26300，Intel Core Ultra X7 358H，16 逻辑处理器，约 31.55 GiB RAM。
- Go 1.27.4、MyGo v0.9.1、官方 Ghostty，CGO=0；原生标签 `mygo_nowebview,mygo_nodownload,mygo_noinspector`，无 e2e automation。
- 正式构建命令：`./scripts/build.ps1 -OutputDirectory build/log-highlighting-release`。复用最终产品代码 `120ade66953b20cae3a578a57bb04e8c2a1d5ece` 的同一 EXE；采样时 Git HEAD 为文档提交 `64f171763f862e9f3a782150365cfde52efd0210`，不是另一份产品二进制。
- EXE SHA-256：`BF52CA24556CBA4C96DFF4136F0168A4854FD3035F85CA04A58CB5584D2023F5`。
- Ghostty DLL SHA-256：`53E8E2DD979702E8F2C48107AF19BE5A76EFC2E88EB7CF1097218E899665DA41`。
- 构建信息为 `vcs.modified=true`，不宣称完全干净的可重现构建。两轮产品代码、二进制、偏好及布局一致；开启轮准备重跑时只延长了采样脚本的连接准备超时，未重新构建产品。
- 窗口 1280×800 DIP，浅色主题，Cascadia Mono 13；100 条连接配置、八标签、四个同时可见终端窗格，连接面板及文件面板展开。通过真实原生窗口连接临时回环 SSH，使用独立数据目录、临时私钥和精确固定的 fixture 主机密钥，不接触用户服务器或配置。

## 负载与计量

使用 [measure-product.ps1](../../scripts/measure-product.ps1)，连接并设置开关后空闲 15 秒，再开始 600 秒负载。fixture 在计时前构建；负载期间不运行构建、测试或其他验收。每会话每 20 ms 发送 20 条日志，目标 1,000 条／秒；每条固定 101 UTF-8 字节，含原有 ANSI 绿色序号、轮换 INFO／WARN／ERROR、ISO 时间、中文、普通 JSON 文本和填充字符。写入受 SSH 背压约束，实际速率须以接收计量为准。

示意内容如下，序号已有显式绿色，行尾为 CRLF，实际还包含填充 `x`：

```text
0000000001 WARN 2026-11-17T12:00:00Z {"message":"性能","id":42} xxx…
```

两轮均加载全部七项内置预设和三条自定义规则（共 161 条编译指令），只有会话开关不同：忽略大小写关键字“性能”紫色、`message` 棕色，大小写敏感 Go 正则 `"id":[0-9]+` 红色。JSON 按普通文本匹配，没有语法解析。完整配色见保存的 environment JSON。开启轮真实窗口复核了日期、级别、自定义颜色、中文软折行和原有绿色序号。

```powershell
./scripts/measure-product.ps1 -SkipBuild -Executable build/log-highlighting-release/windows-amd64/SSHub.exe -Seconds 600 -ScrollbackMiB 2 -PreferencesFile artifacts/log-highlighting-performance/preferences.json
# 开启轮在同样参数后追加 -Highlight，并通过真实窗口为八会话开启高亮
```

偏好输入文件是从保存的 environment JSON 中提取 `preferences` 得到的配置。脚本每约一秒采进程工作集、私有内存和 CPU，并读取最近一条诊断中的原始接收字节、连接／启用／降级数、Go 堆和 goroutine。诊断存在采样滞后；速率由首尾负载样本字节差除以时间、101 和八会话得到，不将接收数据称为屏幕渲染吞吐。CPU 以占满一个逻辑核为 100%，不是任务管理器整机百分比。Go 堆也不包含全部原生终端内存。

高亮轮平均增加单核 16.91 个百分点，约为本机 16 逻辑处理器总容量的 1.06 个百分点。原始接收速率都接近负载目标，不能由此推导产品最高吞吐或所有日志格式的表现。每种条件只测一次，未随机化顺序；开启轮工作集较小不构成“高亮节省内存”的证据。

为避开初始填充，比较负载 60–120 秒与最后 60 秒的样本均值：

| 模式 | 工作集前段 → 末段（MiB） | 私有内存前段 → 末段（MiB） |
| --- | ---: | ---: |
| 关闭 | 182.01 → 183.45 | 187.78 → 189.30 |
| 开启 | 173.80 → 175.02 | 179.57 → 180.35 |

末段相对前段增长较小，本次十分钟内未观察到无界增长；这不替代小时级泄漏测试。历史预算是每终端 2 MiB，不等于同量进程内存，也不能推算固定保留行数。

## 证据与边界

可复核的[关闭轮 CSV](20261118-log-highlighting-data/off-load.csv)、[开启轮 CSV](20261118-log-highlighting-data/on-load.csv)、[趋势统计](20261118-log-highlighting-data/trends.json)及同目录原始 summary／environment JSON 已纳入版本控制。对应完整本机生成物为 `artifacts/product-performance/20261117-235909/`（关闭）和 `artifacts/product-performance/20261118-002640/`（开启）；不将私钥、用户配置、二进制或整个 artifacts 目录纳入 Git。CSV 保留负载阶段，共 593／592 条样本；采样及调度有开销，因此不是精确每秒一条。

早先锁屏尝试 `20261117-223736`、高亮准备超时尝试 `20261118-001540` 都未开始负载，不纳入结果。8 MiB 准备尝试 `20261118-004337` 按用户要求停止，尚未开始负载；测试程序与 fixture 均已退出。准备超时由 600 秒延至 1,800 秒，只影响人工窗口连接准备，不改变负载时长。

无换行提示符的流转换等待另见[微基准](20261117-highlight-matcher.md)：开启 p50 20.402 ms、p95 20.775 ms、最大 25.931 ms，包含调度及 20 ms 拼片期限，不是严格 20 ms 上限或 SSH 到屏幕的延迟。正式负载报告未额外测量端到端输出延迟、交互响应、最高渲染吞吐或固定历史行数。8／32／64 MiB 资源比较已由用户取消；未执行 race（无 C 编译器）、重启冷启动、全新 Windows 或小时级泄漏检查。功能与审查证据见[交付验证](../verification/20261117-log-highlighting.md)。
